# Трекер домашней аптечки

Клиент-серверное приложение для учёта лекарств дома. Что лежит в аптечке, сколько осталось,
когда истекает срок годности и что пора принять сегодня

---

## 1. Доменная область

Человек хранит дома лекарства и принимает их, иногда курсом по назначению врача, иногда
разово. Три вопроса, на которые обычно нет ответа без приложения:

1. **Что у меня вообще есть и сколько?** Упаковки лежат в разных местах, часть начата,
   часть забыта.
2. **Что скоро испортится?** Просроченное лекарство - не просто мусор, а потенциальный вред.
3. **Я уже принял утреннюю таблетку или нет?** И хватит ли запаса до конца курса?

Приложение отвечает на эти вопросы и ведёт журнал приёмов

## 3. Основные сущности


### User - пользователь

`email`, `passwordHash` (BCrypt),
`displayName`.

### Medicine - препарат

Справочник: что это за лекарство вообще. `name`, `inn`
(действующее вещество), `form` (таблетки, сироп, мазь…), `dosage`, `manufacturer`, `notes`,
`unit` - единица, в которой считаются остаток и доза.

### StockItem - упаковка

Физическая упаковка в аптечке. `quantity` (остаток), `initialQuantity` (сколько было),
`expiresAt`, `openedAt`, `status` ∈ {`ACTIVE`, `FINISHED`, `DISCARDED`}, `version`.

Имеет поведение:

- `withdraw(amount)` - не даёт списать из непросроченной упаковки больше, чем в ней есть,
  и сама переводит статус в `FINISHED` при нуле;
- `restore(amount)` - возвращает, не позволяя превысить изначальный объём, и поднимает
  статус обратно в `ACTIVE`;
- `discard()` - выбросили; из такой упаковки принимать нельзя, но история сохраняется;
- `isExpiredOn(date)` - проверка просрочена ли упаковка

### Regimen - курс приёма

Схема: `doseAmount` за приём, `timesPerDay`, `startsOn`, `endsOn` (пусто = бессрочно),
`instructions`, `active`. Производные значения - `dailyDose()`, `totalDays()`,
`isEffectiveOn(date)`.

### IntakeRecord - запись о приёме

`amount`, `takenAt`, `note`. Обязательно ссылается на упаковку (из чего приняли) и
опционально на курс (по схеме или разово).


### Бизнес-логика помимо CRUD

- списание и возврат остатка при приёме и отмене приёма;
- запрет приёма из просроченной, допитой или выброшенной упаковки;
- проверка, что курс и упаковка относятся к одному препарату;
- запрет приёма «в будущем»;
- план на сегодня: сколько доз принято, сколько осталось, хватает ли запаса на сегодня,
  на сколько дней хватит, хватит ли до конца курса;
- FEFO при выборе упаковки на клиенте: первой предлагается годная с ближайшим сроком;
- оптимистическая блокировка остатка, чтобы два одновременных приёма не потеряли друг друга.

## 4. Соответствие методологии 12 факторов

### 1. Кодовая база - одна, под контролем версий, много развёртываний

Проект хранится в Git. Бэкенд и фронтенд - **два отдельных кодбейза**. Это два приложения с
независимыми сборками (Gradle и Vite), независимыми артефактами (jar и статика) и
независимым деплоем.

`.gitignore` исключает всё, что не является исходным кодом: `build/`, `.gradle/`,
`node_modules/`, `dist/`, `.idea/`. Отдельно исключён `.env` - **секретов в репозитории нет**,
вместо него лежит `.env.example` с заглушками и перечнем всех переменных.

Один и тот же кодбейз разворачивается в разных средах: dev и prod отличаются только
значениями переменных окружения и активным профилем, не кодом.

### 2. Зависимости - объявлены явно и изолированы

Бэкенд - `build.gradle.kts` версия самого Gradle зафиксирована в
`gradle/wrapper/gradle-wrapper.properties` и вызывается через `./gradlew`, так что системный
Gradle не нужен и не используется. JDK приходит через `java.toolchain`, а не из `PATH`.
Фронтенд - `package.json` плюс `package-lock.json`, фиксирующий всё дерево до патч-версий.

Версии Spring-зависимостей задаёт BOM Spring Boot. Где BOM не покрывает - указано явно:

```kotlin
testImplementation(platform("org.testcontainers:testcontainers-bom:1.21.3"))
```

 `./gradlew bootJar` собирает самодостаточный jar со всеми
зависимостями внутри; на хосте не требуется ничего, кроме JRE. В образе и JRE своя:
базовый слой `eclipse-temurin:25-jre-alpine-3.23` зафиксирован по версии Java и по версии
Alpine, то есть сборка воспроизводима.

### 3. Конфигурация - в переменных окружения

В `application.yaml` **нет ни одного значения, зависящего от среды** - только плейсхолдеры:

| Переменная | Назначение | Дефолт |
|---|---|---|
| `DB_URL` | адрес БД | **нет** |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | доступ к БД | **нет** |
| `JWT_SECRET` | ключ подписи токенов | **нет** |
| `JWT_TTL` | срок жизни токена | `24h` |
| `SERVER_PORT` | порт | `8080` |
| `APP_CORS_ORIGINS` | разрешённые origin | пусто |
| `LIQUIBASE_ENABLED` | применять ли миграции при старте | `true` |
| `DB_POOL_MAX_SIZE`, `DB_POOL_MIN_IDLE` | пул соединений | `10`, `2` |
| `LOG_LEVEL`, `APP_LOG_LEVEL` | уровни логирования | `INFO` |


### 4. Сторонние службы 

PostgreSQL подключается по URL из окружения. В коде нет ни одного места, которое знало бы,
где именно живёт база: ни хоста, ни имени контейнера. Поменять инстанс - поменять `DB_URL`,
без пересборки артефакта.

Внутри приложения доступ к БД спрятан за выходными портами (`MedicinePersistencePort` и
остальные), так что смена самой технологии хранения тоже не задевает бизнес-логику.

### 5. Сборка, релиз, выполнение - три раздельные стадии

**Сборка.** `./gradlew bootJar` → `build/libs/home_medicine_tracker-0.0.1-SNAPSHOT.jar`.
Код превращается в артефакт, конфигурации внутри нет.

**Релиз.** `Dockerfile` (multi-stage): первая стадия собирает jar на JDK, вторая кладёт его
на JRE и запускает от непривилегированного пользователя. Образ неизменяем; релиз = образ
плюс набор переменных окружения из `.env`.

```dockerfile
FROM eclipse-temurin:25-jdk-alpine-3.23 AS build
...
RUN ./gradlew --no-daemon bootJar -x test

FROM eclipse-temurin:25-jre-alpine-3.23
RUN addgroup -S app && adduser -S -G app app
COPY --from=build /build/build/libs/*.jar app.jar
USER app
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "/app/app.jar"]
```

**Выполнение.** `docker compose --profile full up` - только запуск, без сборки и без правки
кода. Один и тот же образ едет и в dev, и в prod; различает их окружение.

### 6. Процессы - stateless

Приложение не хранит состояния между запросами:

- HTTP-сессий нет - `SessionCreationPolicy.STATELESS`;
- авторизация на самодостаточном JWT: никакого серверного хранилища сессий;
- файлов на диск приложение не пишет;
- кешей в памяти, от которых зависит корректность, нет.

Всё состояние в PostgreSQL. Любой процесс можно убить и поднять заново без потери данных,
и любой запрос может обслужить любой экземпляр.

### 7. Привязка к портам - экспорт через порт

Приложение самодостаточно, встроенный Tomcat и нет внешнего сервера приложений.

Порт задаётся извне: `server.port: ${SERVER_PORT:8080}`. В Compose он отображается наружу
диапазоном `${APP_PORT_RANGE:-8080-8090}:8080`

### 8. Параллелизм - масштабирование процессами

Поскольку процессы stateless (6) и порт назначается извне (7), масштабирование
горизонтальное:

```bash
docker compose --profile full up --scale app=3
```

Корректность при нескольких экземплярах обеспечена **на уровне данных**

- `@Version` на `stock_item`  - оптимистическая блокировка. Два одновременных
  приёма из одной упаковки не потеряют друг друга: оба прочитают остаток 10, но второй UPDATE
  не найдёт строку со старой версией и получит `OptimisticLockingFailureException` вместо
  тихой записи 9 вместо 8.
- уникальные ограничения и внешние ключи живут в БД, а не в коде, поэтому не зависят от того,
  сколько процессов их проверяет.
- Liquibase берёт блокировку в `DATABASECHANGELOGLOCK`, так что одновременный старт трёх
  экземпляров не приведёт к параллельному применению миграций.

### 9. Утилизируемость - быстрый старт и корректное завершение

**Старт быстрый.** Замер на холодном запуске: `Started HomeMedicineTrackerApplication in
5.273 seconds`. Тяжёлых прогреваний нет.

**Завершение корректное.** Настроено плавное выключение:

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

По SIGTERM Tomcat перестаёт принимать новые запросы и даёт текущим дойти до конца, до 20
секунд. 


### 10. Паритет разработки и работы - среды максимально похожи

**Одна и та же СУБД везде**

| Среда                | База                                                   |
|----------------------|--------------------------------------------------------|
| локальная разработка | `postgres:17-alpine` из `docker-compose.yml`           |
| автотесты            | тот же образ `postgres:17-alpine` через Testcontainers |
| прод                 | PostgreSQL 17                                          |


Схему во всех средах создаёт **один и тот же** набор из 9 миграций Liquibase. Сверх этого
`spring.jpa.hibernate.ddl-auto: validate` не даёт схеме и сущностям разойтись


### 11. Журналирование - поток событий в stdout

Приложение пишет логи в stdout как поток событий и не управляет ими дальше. 

Пишутся два слоя. Первый - технические события фреймворка: старт, Tomcat, пул соединений и,
что важнее всего при разборе инцидента, перечень применённых Liquibase-миграций. Второй -
собственные записи приложения в тех точках, из-за которых потом задают вопросы:

| Где | Уровень | Что фиксируется |
|---|---|---|
| `RegisterUserService` | INFO | регистрация: id и email |
| `LoginService` | INFO / WARN | успешный вход; неудачный - отдельно, чтобы видеть перебор паролей |
| `RecordIntakeService` | INFO | приём: кто, из какой упаковки, сколько, какой остаток стал |
| `DiscardStockItemService` | INFO | списание упаковки и остаток на момент списания |
| `ApiExceptionHandler` | WARN / DEBUG | настоящая причина нарушения целостности; отказы по бизнес-правилам |

В prod-профиле вывод структурированный:

```yaml
logging:
  structured:
    format:
      console: ecs
```

Уровни управляются извне: `LOG_LEVEL` - для всего, `APP_LOG_LEVEL` - отдельно для пакета
приложения. Поднять подробность только своего кода, не захлёбываясь в логах Hibernate,
можно без пересборки.

### 12. Администрирование - разовые задачи в той же среде

Главная админ-задача здесь - миграции схемы. Они выполняются Liquibase из **того же
артефакта**, с **тем же** набором changelog-ов и **тем же** окружением, что и обычный запуск

Разовые команды запускаются одноразовым процессом рядом с основным:

```bash
docker compose --profile full run --rm app <команда>
```

- тот же образ, те же переменные окружения, после завершения контейнер удаляется.

## 5. Как запустить

Прописать в .env все необходимые переменные окружения

```bash
docker compose up -d postgres                
./gradlew bootRun                            

Либо все в docker следующей командой:
docker compose --profile full up --build   
```

Фронтенд:

```bash
cd ../home_medicine_tracker_front
cp .env .env.development
npm install
npm run dev                                  
```
